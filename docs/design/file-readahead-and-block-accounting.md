# 文件异步预读与设备 I/O 统计

## 1. 顺序读取

已有页缓存按缺页触发最多 32 页的同步填充；顺序读下一窗口时仍要等待后端。`ReadAheadState` 现在记录最近成功填充的窗口，前台读取经过窗口中点后，让 `PrefetchWorker` 提前加载下一窗口。预读与需求读取共用 `PendingFills`，不建立第二套页缓存。

### 1.1 触发与预算

`prefetch_after_read()` 只在可阻塞运行时存在、文件不是纯内存文件且读取仍顺序推进时请求预读。每个窗口消费一次触发器，随机访问清除顺序状态。工作队列最多保留 16 个窗口，每窗口最多 32 页。磁盘文件的 `disk_reclaim_target()` 下限为 512 页，已大于两个最大窗口；这里没有额外的小缓存分支，也不把保留目标当作当前可用内存。队列饱和或分配失败只放弃推测工作，前台照常按缺页加载。

下一窗口同时受文件末尾和 `u32` 页号边界限制；到达可表示上限就停止预读。任务执行端再次拒绝空窗口和无法转换的起始页，不能将高位截断后误读第 0 页。

`PrefetchWorker` 在安装文件系统运行时时创建一个内核后台线程，由通知对象唤醒。前台复制完数据并释放页缓存锁后入队，后台取出任务后释放队列锁，再访问文件系统。线程句柄和通知由全局 worker 保留，生命周期与文件系统运行时一致。

### 1.2 并发发布

`fill_page_window()` 在短暂的 inode I/O 临界区登记填充所有权，后端读取在锁外执行，发布前重新验证该所有者是否因写入、截断或映射更新而失效。过期填充不会覆盖当前数据。已存在填充或达到填充容量上限时，推测请求直接跳过；需求读取仍使用原有等待与重试行为。

预读失败会结束其填充所有权并唤醒加入者，让需求路径重新尝试真实后端读取，不把推测任务的瞬时错误直接传给后续读取。预读持有 `CachedFile`，因此文件、位置和缓存所有者不会在任务完成前释放。并发删除或卸载仍受既有所有者准入约束，预读没有新增绕过关闭流程的入口。

## 2. 设备计时

`DeviceIoMetrics` 属于一个 `BlockDeviceHandle`，代替原先将全局请求计数放到根设备名下的做法。`RequestAccounting` 随唯一 `CompletionSender` 移动，统计生命周期与驱动拥有请求的生命周期一致，不由等候线程是否继续等待决定。旧全局 `block_io_stats()` 及其四个累计计数已删除，NVMe 回归通过 `root_block_stats()` 使用根设备句柄的同一份统计，避免跨设备累计值掩盖未发生的目标设备 I/O。

### 2.1 统计口径

运行时确认驱动移走请求前缀后、提交门铃前启动计时。完成被消费时终止计时；软件通道中等待、未被接受的重试和分派前拒绝不计入设备在途时间。接收端取消不结束计时；异常丢弃已开始的发送端按失败终止一次记账。

`BlockIoStats` 使用单调时钟纳秒和 512 字节扇区。读、写、flush 分别累计请求数和时间；忙碌时间是至少一个在途请求的区间并集，加权时间是“在途数乘时间”的积分。失败请求计入请求数和失败数，不宣称其全部扇区已成功传输。快照会先累计仍在途的区间，不能把正在运行的设备显示为空闲。

### 2.2 用户态呈现

StarryOS 的 `render_diskstats()` 将根块设备快照按 Linux 字段顺序输出，时间转换为毫秒，合并与 discard 字段保持零，因为当前路径没有相应操作计数。这里测量的是本内核驱动接受到终结的时间，不能把它称为纯介质服务时间，也不能直接等同 Linux 块层不同边界的统计。

`root_block_stats()` 在根不是块设备（如内存根）、根设备记录尚不可用或其 `Weak<BlockDeviceHandle>` 无法升级时返回 `None`；`render_diskstats()` 随之返回空字符串，因此成功读取 `/proc/diskstats` 会得到零行。空结果表示当前没有可导出的根块设备快照，不能据此推断 I/O 活动为零、系统没有磁盘或读取失败；读取失败仍由打开和读取操作的错误返回判断。该接口不枚举其他磁盘，也不补造全零的 `blk0` 行。

监控消费者应将空结果标为“无数据”，清除此前的计数与速率基线，不延续旧速率，也不猜测设备行；设备行重新出现后，先按设备身份建立新基线，再用后续有效样本计算速率。`apps/starry/monitor` 的 `GlancesHeadlessCarpet.py` 与 `NodeExporterCarpet.py` 当前要求 NVMe 根盘 `nvme0n1` 的非零启动读计数，不覆盖空结果及恢复后的速率计算；本次仅明确接口约定，没有修改这些消费方。

## 3. 设计选择

保留单一后台预读线程可以限制 speculative I/O 对需求读和编译任务的影响。直接在前台同步读取下一窗口会扩大缓存命中路径的尾延迟；为每个文件创建线程会让大量 crate 文件带来无界线程数。独立第二套缓存会重复失效和关闭协议，故沿用现有 `FillOwner`。

### 3.1 预期收益与风险

收益来自计算与下一窗口 I/O 重叠，以及已有块队列可以接收多个独立请求。收益大小取决于顺序比例、缓存命中和实际设备并行度，不能由最大窗口和队列深度直接推算编译加速倍数。预读可能读取未消费的数据，因此限制窗口和队列，并用真实冷编比较读扇区、忙碌时间与总时间。

### 3.2 验证边界

组件用例证明顺序命中只排队而不在前台读取后端、后台填充可被后续需求命中，以及重叠请求的忙碌与加权时间关系。完成通道用例验证接收端取消后仍准确完成一次统计、未分派请求析构不计数。已有填充回归继续保护并发写入、截断、映射与卸载语义。

组件用例之外，定向系统测试负责核验真实文件读写、私有映射和关闭路径；具体提交的执行结果与未覆盖项记录在对应 PR 验证材料中。板卡性能比较使用同一份源码、Cargo.lock、工具链、Linux 构建的 tg-xtask 与新建 target 目录；失败运行不能纳入成功性能数据，也不能把组合分支的收益归为单项改动。
