# 页缓存命中读取并发：设计与验证计划

## 问题和边界

32 MiB 缓存窗口的 mutex 等待中，CachedFile::read_at 的 io_lock 调用点占
81.0739%（见 large-file-cache.md）。当前每个读页在检查是否命中之前就获取
io_lock；因此读取已缓存页也必须等待其它页的 backing I/O。命中等待占其中
多少尚未被单独量化，必须通过独立实验确认整机收益。

不能直接删除此锁：resize::prepare_zero_write_locked 会先修改缓存，再尝试
backing write/set_len，失败时恢复原数据。绕过锁的读者可能观察到最终失败操作
的中间零值。写入、append 和可修改缓存页的回调也必须保留相同排他边界。

## 候选方案（本地实现、验证中）

保留所有慢路径、写回和截断的 io_lock。每个 CachedFileShared 增加一个仅由
io_lock 持有者设置的更新状态；RAII 更新 guard 在任何缓存内容修改前发布
“更新中”，在全部成功或错误回滚完成后清除状态，最后释放 io_lock。

命中快路径只在 page_cache 锁内检查更新状态并把已缓存内容复制到内核 scratch。
若更新中、页不存在或不能取得缓存锁，先释放缓存锁再走原 io_lock 路径。
用户缓冲区写入仍在所有缓存锁外进行，不能把用户缺页引入新的锁顺序。

更新状态覆盖 write_at、append、set_len 和 with_page_or_insert 的可修改回调。
只从 backing 装入缺失页的读取不发布更新状态；其它页的缓存内容在装载期间
保持原样。缓存锁保证装入、复制和回收之间不会留下悬空页引用。
状态发布与缓存锁必须共同证明：读者要么在线性化点前看到旧的稳定内容，要么
等待整个修改/回滚完成，不能看到临时内容。状态本身不是页内容或长度的副本。

此前记录的 MOSS dc54e032/45543403 提交对象在当前本地参考仓库已不存在，
不能继续把它们当作已核验的版本标识。本轮实际读取的参考仓库
`moss-smp-scheduler-optimization` HEAD 为 5a54e4413c9657bfb531cc32f6d688090465200d，
`kernel/src/mm/aspace/mod.rs::handle_page_fault_concurrent_inner` 的三阶段方案把
I/O 移出地址空间锁，并在提交前重检 VMA/PTE。其 folio 方案涉及新的共享页所有权。
本候选只处理 CachedFile 的命中读取，
不移植页表并发提交、只读直映、物理页引用或新的睡眠读写锁，不增加公共 API。
替代方案是继续扩大容量或保持原状；容量能减少 miss，但不能允许不同页的
命中和未命中读取同时前进。代价是读命中多一次状态检查、修改路径维护一个
严格受 io_lock 保护的 RAII 生命周期。

## 验证门槛

1. 在真实 CachedFile 上预热页，保持用于缺页装载的 io_lock 被占用，确认命中
   读取路径不需要该锁；旧实现必须确定性失败，不能只比较线程执行时间。
2. 在真实 set_len 的 backing 失败点观察已准备但未提交的缓存尾部，确认快路径
   拒绝复制；失败后正常 read_at 必须读回完整原内容，输出缓冲区不得残留临时零值。
3. 覆盖正常写入、append、页回调、缓存缺失和回收，检查 RAII 在错误出口清除状态。
4. 完整缓存测试、目标 clippy 和格式检查通过后，只运行一个新 600 秒 QEMU 窗口。
5. 比较活跃 CPU、读取等待和编译进度；检查退出状态、哈希和文件系统一致性。

这是新的并发快路径，属于高风险局部设计。实现合入前需要边界维护者审核；
不能把设计文档或普通构建通过当作并发正确性证据。当前正在测量的 256 MiB
内核不包含该方案。

## 256 MiB 窗口后的决策

新窗口已完成：ext4 全局锁占 mutex 等待 69.9461%，缓存 read_at 的 io_lock
降到 27.3822%。当前优先检查 ext4 同步写盘路径，本方案保留为未实施草案，
不因为已经写了设计就绕过新数据改变优化优先级。

## inode-identity 窗口后的决策

本轮 604.512285776 秒，CPU 活跃 11653/47417 = 24.5756%，31 个编译单元。
mutex 总量 2553842349088 ns；ext4 锁调用点 1703372746416 ns（66.6984%），
缓存读取 io_lock 调用点 776923071136 ns（30.4217%）。用户缺页入口覆盖的
mutex 栈累计 1053273134368 ns（41.2427%）。等待类别有包含关系，不能相加
视为墙钟时间；缓存命中与缺失在该等待调用点仍未分开统计。

用户要求优先缺页优化。本轮选择先完成此命中并发边界，再实施 MOSS 风格
锁外缺页准备/锁内重检提交。当前缓存 liveness 测试已在旧实现确定性失败：
持有 io_lock 时真实 read_at 无法完成，exit 101，错误为 Timeout。
加入更新 guard 后必须同时验证失败截断不会被读者观察到临时零值。
地址空间三阶段改造单独记录设计和回归，不把缓存命中改造冒充完整移植。

## cache-hit 独立窗口实测

实现后缓存/文件系统 host 测试 98/98 通过，`cargo xtask clippy --package ax-fs-ng`
8/8 通过。liveness 旧实现先失败后通过；故意移除更新状态检查，失败截断测试
实际读到临时零值，退出 101，恢复检查后通过。没有通过放宽断言接受临时内容。

`cache-hit-window-600` 采样 605.941400512 秒；8 vCPU 活跃样本为
13551/47379 = 28.6013%，idle 71.3987%。启动 36 个编译单元、33 个 crate，
窗口 rc=124，完整编译未完成。tg-xtask 与源码归档均复用；5 项输出 SHA-256
全部匹配，关闭 QEMU 后 `e2fsck -fn` 退出 0。已实际查看 mutex 和 active CPU 图。

mutex 累计等待 2415972710960 ns。用本轮 ELF 核对调用点：
`Ext4Filesystem::lock` 1973600628528 ns（81.6897%），
`FileBackend::read_at` 的缓存慢路径 372563637808 ns（15.4209%）。
用户缺页 mutex 栈累计 674306010048 ns（27.9103%），上一轮为
1053273134368 ns（41.2427%）。这些是多任务累积且调用链可重叠的等待，
不是单次缺页延迟或可直接相加的墙钟时间。

上一轮 inode-identity 原型同时存在较宽的身份快路径；本轮已经缩小为仅 ext4，
因此 31→36 单元、24.58%→28.60% 活跃的单次变化不能全归因于缓存命中优化。
相比更早 metadata-writeback 的 34 单元、27.50%，整体仍只有有限改善。
CPU 7 活跃 83.84%，其它核约 13.99%–40.14%，低 CPU 利用问题仍未解决。
