# 大文件页缓存容量实验

## 假设和证据边界

600 秒 VMA 优化窗口中，文件缓存 read_at 的 io_lock 调用点占 mutex 累计等待
2,459.689 / 2,872.066 秒；块读取 217,049 次、累计 409.075 秒。源码每个磁盘
文件固定最多缓存 512 个 4 KiB 页（2 MiB），缺页读取即使命中缓存也先获取 io_lock，
未命中时持有此锁进行 backing I/O。因此，大文件工作集超出 2 MiB 后重复淘汰
可能延长持锁时间并阻塞其它读者。现有 guest 样本未记录命中/未命中计数，
尚不能把容量不足写成已验证的整机根因。

计划以真实 CachedFile 进行两次 4 MiB 读取，计数 FileNode backing read 调用，
验证容量不足确实能导致重复 I/O；再在同一 QEMU 冷构建中验证候选，失败则回退
该候选，不把低层 I/O 次数下降当作整机提速。

## 设计与替代方案

保持 io_lock 及截断、写回、映射淘汰协议不变。小文件保留现有 512 页下限；
对打开时已经较大的文件，按长度提高 LRU 上限，最多 8,192 页（32 MiB）。
缓存数据页仍按需分配，全局 clean-page reclaim 保留。上限是候选参数，不是
为 rustc、路径或单一测试建立专用分支。

不能把所有文件的固定上限直接改为 8,192：仓库锁定的 lru 0.16.4 中，
LruCache::new 直接调用 HashMap::with_capacity，因此 LRU 的索引会预留容量。
按文件长度限定可避免所有小文件都承担大索引。代价是大文件可保留更多页，
并增加其索引开销；需要观察内存压力、reclaim 和文件系统一致性。
本轮不新增动态增长策略，因此从空文件逐渐写大的输出仍保留原容量。
32 MiB 只是每个大文件的数据页上限，不是全局内存预算，也不意味着打开文件时
立即分配全部数据页。全局回收机制本身的并发协议不在此容量候选中变更。

删除 io_lock 或允许缓存命中绕过它，会触及截断失败回滚的中间状态；引入读写锁、
每页装载状态或 MOSS 的 folio/只读直映涉及新的并发和物理页所有权，不是本轮
容量实验的必要条件。内部已检查 cache/mod.rs、resize、reclaim、writeback 与
现有缓存回归；MOSS 的迁移记录提供页缓存方向，但不直接移植其组合实现。

这是影响性能和内存上限的局部实验，合入前仍需要边界维护者审查。本轮不改变
syscall 返回值、磁盘格式、缓存脏页规则、锁顺序或用户缓冲区访问时机。

## 实现与确定性回归

CachedFileShared::new 按打开时长度计算容量，并保持 512 页下限和 32 MiB 上限。
真实 FileNodeOps 测试后端记录 backing read 次数；同一个 4 MiB CachedFile 连续
完整读取两遍，并逐字节校验内容。旧容量下第一遍 32 次，第二遍累计 64 次，
“第二遍无需新增 backing read”的回归断言失败（exit 101）。修改容量后同一用例
通过。另一用例验证空文件、4 MiB 和 u64::MAX 长度对应容量 512/1024/8192，
构造时实际数据页分配数均为 0。

以下验证均通过：

- `cargo test -p ax-fs-ng --lib --features host-test,ext4,vfs`：91 项通过。
- `cargo fmt --package ax-fs-ng`。
- `cargo xtask clippy --package ax-fs-ng`：8 项检查全部通过。
- `cargo xtask starry build -c apps/starry/macos-selfbuild/build-aarch64-unknown-none-softfloat.toml`。

### 下一项独立候选：256 MiB 上限

离线检查实际根镜像确认 librustc_driver-596a22bf48e1ea3e.so 长度为
294,649,336 字节。对应预构建库的 ELF LOAD 只读段为 0xc7b8660 字节，
另有 0x45f800 字节的文件支持读写段；因此 32 MiB 不足以保留整个加载区间。
这不证明全部加载区间都是热区，只说明还有容量淘汰假设需要验证。

下一轮将同一策略的每文件上限从 32 MiB 提到 256 MiB，保留按文件长度限制、
小文件下限、按需分配和全局 reclaim，仍不改变任何锁协议。该上限能覆盖此
加载区间，但不匹配文件名、工具链或路径。代价是单个大文件可占用更多缓存
和索引，不能直接作为所有内存规模机器的长期默认值；本次固定 8 GiB QEMU
实验必须观察 OOM/reclaim、CPU 利用、等待和进度。没有足够收益则回到已测
32 MiB 候选，不通过删除一致性约束来获得性能。

真实双遍读取回归已扩大到 64 MiB：32 MiB 容量下断言稳定失败（exit 101），
backing read 从第一遍 512 次增加到两遍 1,024 次。提高上限后，同一回归通过；
全部 91 项缓存/文件系统测试、8 项 clippy、cargo fmt 和目标内核构建均通过。
容量边界用例更新为最大 65,536 页，仍验证构造时没有分配实际数据页。

QEMU 目录为 `target/profiling/arceos-helloworld/starry/cache-256m-window-600`，
于 2026-09-10 00:55（Asia/Shanghai）启动。
