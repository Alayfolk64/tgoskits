# Orange Pi 5 Plus run20 failure report

## Conclusion

run20 did not fail because the 20-minute watchdog lease expired. The build
failed after StarryOS ext4/JBD2 exhausted transaction credits and returned
`ENOSPC` while the physical filesystem still had free capacity. The workload
wrapper then returned a failure and the outer init script executed
`reboot -f`. The forced reboot happened while the StarryOS-mounted Linux root
filesystem contained inconsistent Cargo build metadata.

The next Linux boot was not guaranteed to run fsck because restoring
`/boot/boot.scr` did not add `fsckfix` to the Linux command line. Recovery only
completed after U-Boot was interrupted and `extraboardargs=fsckfix` was set for
the boot. Initramfs then repaired the filesystem successfully.

## Failure sequence

1. StarryOS booted with 8 CPUs and armed the hardware watchdog:
   `requested=30s actual=44.739242666s feed=10s lease=1200s`.
2. Before starting the workload, StarryOS restored the active Linux boot
   script and printed `LINUX-BOOT-RESTORED state=switched`.
3. The workload ran
   `tg-xtask arceos build --package arceos-helloworld --arch aarch64`.
4. At kernel time 171.206 seconds, ext4 first reported
   `no space is available: jbd2:handle_credits`.
5. Cargo had reached 93/246 units. Removal of two `somehal-macros` object files
   then failed with `No space left on device (os error 28)`, and Cargo exited
   with status 101.
6. The wrapper recorded `command_rc=1` and elapsed time
   189.912167084 seconds, then returned failure.
7. The outer init script ran `sync`, unmounted the `/proc`, `/dev`, and `/sys`
   bind mounts, ran `sync` again, and unconditionally executed `reboot -f`.
8. Because the watchdog lease was 1200 seconds and the workload failed at
   about 190 seconds, this reboot was initiated by the script, not by watchdog
   expiry. The watchdog remained only a fallback.

## Filesystem damage and recovery evidence

The recovery boot ran:

```text
fsck -C -y -V -t ext4 /dev/mmcblk0p1
```

The full output is saved as `fsck.log`. It reports:

- `armbi_root contains a file system with errors, check forced`;
- many Cargo `target` inodes containing garbage;
- directory entries referring to deleted or unused inodes;
- incorrect inode reference counts;
- block bitmap, inode bitmap, free-block, and free-inode inconsistencies;
- `armbi_root: ***** FILE SYSTEM WAS MODIFIED *****`;
- fsck status 1, meaning errors were corrected.

The repaired root filesystem now reports `Filesystem state: clean`, and its
`Last checked` timestamp is the recovery boot time. Linux subsequently reached
`graphical.target`; `systemd-analyze time` reports 6.636 seconds in the kernel
and 3.421 seconds in userspace.

The active `/boot/boot.scr` SHA-256 is
`d47fa003c0210128b863a04301e17ec56b7957cb3b3b2c80c1d467ee99c965e9`,
identical to both Linux backup copies. The StarryOS script has a different
SHA-256, `383e3b0e3979978ef1883fe7076707b740a9d0d8b3414d9223dd129437518002`.

## Recovery-chain defect

`restore_linux_boot.sh` verifies and restores the Linux `boot.scr`, but the
Linux `/boot/armbianEnv.txt` only contains `extraargs=cma=256M`. It does not
contain `fsckfix`. Therefore an automatic return to Linux after an unsafe
StarryOS reset does not guarantee an offline filesystem repair before the root
filesystem is mounted.

The StarryOS U-Boot script is also not self-restoring. It only loads the FIT,
sets the StarryOS root and init command, and calls `booti`. Linux boot recovery
currently depends on StarryOS reaching the user-space init script and running
`restore_linux_boot.sh`. A kernel failure before that point can leave
`boot.scr` pointing to StarryOS and require a manual U-Boot interruption.

## JBD2 credit root-cause analysis

The failed object files do not require unusually large ext4 transactions. The
larger `somehal-macros` object has one contiguous 31-block extent, the smaller
object has one data block, and their indexed parent directory has four leaf
blocks. The filesystem still had about 33 GiB free. This rules out physical
capacity exhaustion and a deep extent-tree teardown as explanations for the
reported `ENOSPC`.

StarryOS reserves 24 metadata credits for unlink, matching Linux
`EXT4_DATA_TRANS_BLOCKS` on an extent filesystem without quota. Linux performs
directory lookup before starting that handle and lets only metadata explicitly
touched by the unlink join it. Linux buffer reclaim also refuses dirty,
writeback, referenced, or JBD2-owned buffers; reclaim does not synchronously
write unrelated dirty metadata through the current ext4 handle.

The rsext4 caches violated that ownership boundary in three places:

- an inode-table miss evicted the least-recently-used inode and synchronously
  wrote it when dirty;
- a bitmap miss did the same for an unrelated dirty group bitmap;
- data-block pressure wrote a quarter of the LRU set before admitting the
  requested block.

The inode and bitmap writes were charged to whichever JBD2 handle happened to
trigger the cache miss. Under the compiler's high inode churn, an unlink could
therefore spend its bounded credits on metadata from earlier operations and
surface `jbd2:handle_credits` as a false `ENOSPC`. The data-cache path also
allowed cache pressure, rather than the explicit writeback owner, to choose
when dirty blocks reached the device.

Deterministic unit regressions reproduced the ownership defect before the
fix: with a one-entry cache containing an unrelated dirty item, a cold lookup
evicted that item and performed hidden write I/O. The inode and data regressions
both failed on the run20 implementation. The cache policy was then changed as
one unit:

- capacity pressure reclaims only clean entries;
- dirty entries may temporarily exceed the configured soft limit;
- only explicit `flush`, `flush_all`, or semantic eviction paths perform
  writeback.

After the change, the previously failing inode regression passes, all three
inode/bitmap/data ownership regressions pass, all 15 data-cache tests pass,
and all three targeted clippy configurations pass. The complete rsext4 library
suite passes all 433 tests. Linux-image HTree delete/rename validation and the
final-unlink/explicit-reap lifecycle test also pass. The complete package run
passes 655 tests: 433 library tests and 222 integration tests. This proves and
fixes the hidden-write mechanism locally. The design and rollback constraints
are recorded in `docs/design/rsext4-cache-writeback-ownership.md`.

This is not yet a claim that run20 is fixed on hardware: no board reboot or
StarryOS run was attempted while unattended. The next attended board run must
verify that the full 246-unit build completes without `jbd2:handle_credits`,
followed by the mandatory Linux fsck check.

## Required safeguards before another board run

1. Ensure every post-StarryOS Linux boot carries `fsckfix` before switching
   `boot.scr` to StarryOS.
2. Make the StarryOS boot selection one-shot at the bootloader boundary, so
   failure before StarryOS user space cannot leave the board in a StarryOS boot
   loop.
3. Replace unconditional `reboot -f` with an exit path that stops new writes,
   waits for sync, remounts the shared root filesystem read-only when possible,
   and only then resets. Keep the watchdog as the last-resort fallback.
4. Treat `jbd2:handle_credits` as the run20 primary kernel defect. Do not retry
   the workload until its transaction-credit exhaustion is understood or the
   test is protected from corrupting the reusable Linux root filesystem.
5. After every StarryOS write test, verify the initramfs fsck result and the
   Linux root filesystem state before starting the next run.

## Immediate board safeguard applied

While the board remained in the recovered Linux system, `/boot/armbianEnv.txt`
was atomically updated to contain `extraargs=cma=256M fsckfix`, followed by an
explicit `sync` and hash verification. Its SHA-256 is
`192db2ad52a2fe2b3d54b7b3028ebe9506bddfc0907922be0dbd7a94e7a276a2`.

The previous file is retained as
`/boot/armbianEnv.txt.before-forced-fsck-20260921`, SHA-256
`db532323132d1f11ef1a3cb3a214bfe07a6be0b54480c1d862f61fd4fe0d1b71`.
No reboot was performed. The active `boot.scr` remained the verified Linux
script. Any subsequent ordinary Linux boot will therefore request initramfs
fsck without requiring a manual U-Boot environment override.
